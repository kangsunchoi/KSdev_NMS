## 2026-06-02 초기 생성 (Emergent)

- Emergent AI로 생성. 저장소의 `memory/PRD.md`, `test_result.md`, `test_reports/`, `.emergent/`가 이때 산출물
- 1차 구현
  1. 장비 CRUD, 알람(목록/확인/삭제), 토폴로지, 대시보드 요약, 목업 생성/초기화 API
  2. 5초 주기 시뮬레이션 루프 (지표 흔들기 → 상태 판정 → 알람 자동 생성)
  3. 화면 4개: Dashboard, Devices, Topology, Alerts
- 2차 구현 (iteration 2)
  1. 지표 히스토리(`device_metrics`, 24h TTL)와 차트 모달
  2. 알람 일괄 확인, 장비/알람 텍스트 검색
  3. WebSocket(`/api/ws`) 5초 푸시, CSV 내보내기
- 디자인 기준: 배경 `#1a1a2e`, 강조 `#16c79a`, Inter + JetBrains Mono

## 2026-06-03 개발 가이드 작성

- Cisco IND 벤치마킹, Core-Adapter-Profile 3계층, 8 Phase 로드맵(20~24주) 정리
- 핵심 결론: Emergent 앱은 관리/시각화만 맡고, 수집은 Node-RED 같은 외부 도구가 맡는 구조("앱은 뇌, 수집기는 감각기관")
- Go로 Core를 다시 짜는 대신 기존 React + FastAPI + MongoDB 앱에 수집 API를 붙이는 Pragmatic 경로를 선택

## 2026-06-03 ~ 06-05 Pragmatic 경로 구현

대화: "NMS 프로젝트 코드 리뷰 요청"

1. 코드 리뷰
   - 앱이 ksdev와 별개인 관제 앱이고, iteration 2까지 진행된 상태임을 확인
   - 배포 전 이슈 6가지 정리: 포트 충돌(8000), WebSocket 프록시 헤더, DB 이름 분리, `requirements.txt`의 설치 불가 패키지, `.env` 미커밋(정상), README placeholder
2. ksdev와 같은 VM에 공존 배포
   - NetVision 대시보드 `:8080`, 백엔드 `:8001`(systemd `netvision-backend`), DB `netvision`
3. 수집 입구 추가 (`backend/server.py`)
   - `POST /api/ingest`(ping/SNMP 지표), `SIMULATION_MODE` 토글, `GET/POST /api/sim/mode`
   - 상태 판정을 `_derive_status()`로 공용화해서 시뮬과 실데이터가 같은 기준으로 판정
4. Node-RED 설치
   - 사용자 보안 설정 Yes(관리자 계정, full access), Projects 기능 No, `ufw allow 1880/tcp`
5. 수집 플로우 6종 작성: ping 수집, 서브넷 디스커버리(fping), SNMP 식별(sysObjectID), SNMP CPU, LLDP(스캐폴드), Modbus 시뮬+수집
6. 알람 자동 해소
   - 장비가 online으로 회복되면 미확인 알람 자동 확인 처리
   - 통지 채널은 사용자 선택으로 이때는 보류("일단 자동 해소만")
7. 토폴로지 링크 엔진: `links` 컬렉션, `POST /api/links`, 수동 링크로 엣지 표시 확인 [확인]
8. 범용 지표(UnifiedMetric): `POST /api/metrics`, `device_kv`, `unified_metrics`
9. Modbus 수집: Node-RED 내 Modbus 서버 노드로 시뮬, 바이트/워드(빅엔디안) 문제 해결
10. 작업 기록 문서 작성: `원본_NetVision_OT_구현기록_pragmatic.md`

## 2026-06-06 ~ 06-07 실장비 테스트 환경 준비

대화: "NMS 개발 남은 작업"

1. 범용 지표 화면 표시
   - `MetricChartModal`에 최신값 카드와 명명 지표 시계열 추가 (`/kv`, `/series` 사용)
2. 목업 정리 API
   - `POST /api/devices/cleanup` (이름 접두어 + IP 접두어 조건, `dry_run` 미리보기 기본)
3. CDP 수집 플로우 (`netvision_cdp_flow.json`)
   - exec + snmpwalk 방식, `cdpCacheTable` → `/api/links`. 스캐폴드 상태
4. 목업/Emergent 흔적 제거
   - Dashboard, Devices의 "Seed Mock", "Generate 20" 버튼 제거 (기존 장비를 지우고 목업 20대를 다시 만드는 동작이라 실장비 환경에서 위험)
   - `public/index.html`의 Emergent 배지, PostHog 분석 스크립트, 페이지 제목 정리
   - 실데이터 전환 순서 확정: `SIMULATION_MODE=false` 적용 후 `mock/reset`
5. 디스커버리 탭 (`pages/Discovery.jsx`)
   - 화면에서 IP 대역과 SNMP community 입력 (현장마다 community가 달라서)
   - 백엔드는 설정만 저장(`/api/discovery`), Node-RED가 `run_requested=true`를 폴링해서 fping 스윕 → `POST /api/discovery/register`(중복 제외)
   - 192.168.0.0/24에서 Cisco IE3x00, IE2000 등 수집 [확인]
6. 인터페이스 모니터링
   - `POST /api/interfaces`(연속 카운터로 bps 계산), `GET /api/devices/{id}/interfaces`, `InterfaceModal`
   - Node-RED 인터페이스 플로우 작성
7. 인터페이스 수집 디버깅
   - 백엔드 정상(`matched:true`), 장비 SNMP 정상인데 수집 0건
   - 원인: `snmpbulkwalk`에 서브트리 여러 개를 주면 첫 번째만 수집됨
   - 해결: `ifTable`(`1.3.6.1.2.1.2.2.1`) 단일 walk로 변경
   - 192.168.0.240 수동 주입으로 13포트 저장 및 화면 표시 확인 [확인]
   - 자동 플로우(ifTable 버전) Import/Deploy는 사용자가 다음에 하기로 하고 종료 [미확인]

## 2026-06-07 IND 비교 및 기능 일괄 개발

대화: "개발 남은 작업 정리"

1. Cisco IND 기능 비교
   - IND 4대 기능: Operate(Alarms, Assets, Traffic, Port), Inventory, Topology, Settings(RBAC, Audit)
   - 저장소 코드를 직접 보니 문서보다 앞서 있었음: 지표 화면, 인터페이스/트래픽, 포트 상태는 이미 완료
2. 범위 결정 (사용자 결정)
   - IND 기능은 전부 넣는 것을 목표로 함
   - PLC는 실장비가 없으므로 시뮬로 개발, 테스트, 개선
   - Cisco 전용 4종(Device Pack, IOS 이미지 업그레이드, ISE pxGrid, PnP)은 보류, 최하위
3. 최종 로드맵 확정 (Phase 1~7, `05_남은작업.md` 참조)
4. Node-RED 플로우 export를 할 일로 등록 (사용자가 외부에 있어서 보류)
5. 코드 작업 (사용자 요청: "한 번에 배포해도 오류 없는 선에서 최대로")
   - 원칙: 추가 패키지 없음(표준 라이브러리만), 신규 기능은 `.env` 토글 기본 OFF
   - 인증/RBAC/감사: `auth.py`, `audit.py`, `Login.jsx`, `lib/auth.js` (미들웨어 시나리오 테스트 11건 통과)
   - 알람 RCA(상위 장비 장애 연관 표시)와 통지(`notify.py`, Slack/Telegram)
   - 미관리 세그먼트 탐지(FDB + LLDP), 논리 자산(PLC 하위 IO), 시뮬 모드 시드 데이터
   - 토폴로지 WebSocket 갱신 시 LLDP/세그먼트가 사라지던 버그 수정 (`/api/topology` 10초 주기 갱신)
   - Alerts 화면 RCA 배지, Settings 화면(사용자 관리, 감사 로그)
   - 한/영 i18n 전 화면 (기본 한국어, 사이드바 KO/EN 토글, 기술 약어는 영어 유지)
6. 최종 통합 배포 세트 20개 파일 (신규 8, 덮어쓰기 12) → 저장소 반영 [확인: 2026-06-07 커밋]
   - VM 배포 후 화면 동작 확인 기록은 없음 [미확인]
7. 토폴로지 아이콘 매핑 확정 (lucide): switch=`network`, plc=`cpu`, hmi=`monitor-smartphone`, sensor=`radio-receiver`, 미관리 세그먼트=`cloud`, 논리 자산=`box`. 저장소에는 아직 미적용 (현재는 도형으로 구분)
8. 다크/라이트 테마는 하드코딩 색상 약 92곳 토큰화가 필요해서 백로그(낮음)로 등록

## 2026-06-07 OCI 이전 검토

대화: "오라클 서버에 작업물 업로드하기"

- NetConfig Builder(ksdev)가 돌고 있는 OCI 서버로 NMS를 옮기는 안 검토
- OCI에서는 VPN이 없어 사내 192.168.0.0/24 장비에 SNMP/ping이 불가 → 시뮬 모드만 가능
- 결정: OCI는 ksdev만, NMS는 내부 VM(192.168.108.129) 유지. 이전 작업 없음

## 2026-06-07 토폴로지 포트 번호 표시 점검

대화: "토폴로지에서 인터페이스 포트 번호 확인"

- 백엔드 `/api/topology`는 링크 엣지에 포트 라벨(`"Gi0/1→eth0"` 형식)을 이미 넣어줌
- 프론트 Cytoscape 엣지 스타일에 `label` 속성이 없어서 화면에 표시 안 됨
- 남은 일: 엣지 라벨 스타일 추가(프론트 소규모 수정) + LLDP 실파싱 확정

## 2026-09-15 ~ 09-16 비인가 자산 탐지 설계

대화: "비인가 자산 표시 방식 검토"

1. 상용 제품 조사: Siemens SINEC NMS, Moxa MXview One, Cisco IND/IAD/Cyber Vision의 비인가 자산 식별 방식
2. Cisco IAD는 SNMP/YANG 미지원이라 SSH CLI(`show iad inventory`) 파싱 의존, 한계 정리
3. 미관리 스위치 탐지: 공식 지원은 Hirschmann HiVision의 FDB 추론 정도. 일반 문제로는 NP-hard라 "Hidden L2 후보"까지만 판단하는 것이 맞다는 결론
4. 비인가 자산 식별 방법 정리(스위치 정보 활용, 강제형, 패시브, 능동 스캔)
5. 사용자가 제시한 파이프라인(Syslog → CAM → DELTA → Global MAC DB → Asset DB 대조 → ISSUE)과 3원칙 검토, 보완점 도출
6. 구현 스펙 작성: MongoDB 스키마, 포트 역할 판정, 전이 로직, 억제 규칙, API, Node-RED 수집기, 단계 적용
7. 상태: 설계만 완료, 코드 구현 안 됨 → `06_설계_MAC_Observation.md`

## 2026-10-23 토폴로지 꺾은선 링크 검토

대화: "NMS 토폴로지에서 꺽은선 링크 그리기"

- Cytoscape `curve-style: 'taxi'`(직각 꺾은선) 제안, 대안으로 `segments`
- 필요 조건: Cytoscape.js 3.18 이상. 저장소 `package.json`은 `cytoscape ^3.34.0`이라 충족 [확인]
- 주의: 같은 두 노드 사이 병렬 링크는 겹칠 수 있음, 한 스위치에서 여러 장비로 갈라지는 지점은 `taxi-turn` 조정 필요
- 현재 저장소 `Topology.jsx` 엣지는 `bezier` 그대로 → 미반영
